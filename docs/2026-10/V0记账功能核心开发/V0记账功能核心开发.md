## 2. V0 定位与范围

### 2.1 定位

V0 是项目**第一版最小可运行切片**：单用户、免登录，聚焦"**记账闭环**"——先建好基础信息（账目/渠道/科目），再完成三类记账（单次/双次/分期）与明细查看、最小汇总。V0 跑通后，V1 在其上补齐账单、贷款汇总、完美账单、导入导出等完整账务，V2 再加多用户/登录/家庭。

### 2.2 V0 / V1 / V2 关系

| 版本 | 范围 | 说明 |
| --- | --- | --- |
| **V0（本期）** | 记账功能核心 | 基础信息 + 三类记账 + 明细列表 + 最小汇总 |
| V1 | 完整账务 | 账单管理、贷款（含提前还款/汇总）、完美账单（套现）、导入导出 |
| V2 | 多用户协同 | 登录/注册/改密、家庭管理（成员/用户组/配置授权）、WebView 客户端（后续） |

### 2.3 功能清单（V0）

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| V0-F1 | 基础信息管理 | 账目类型（trade）、交易渠道（card）、记账科目（subject）的增删改查 |
| V0-F2 | 记账（单次） | 消费 / 收入 / 调账，一条流水 |
| V0-F3 | 记账（双次） | 还款 / 调账，from/to 两条流水，同一交易编号 |
| V0-F4 | 记账（分期） | 消费/账单/理财分期：一笔分期 + 按期多条流水 |
| V0-F5 | 明细列表 | 查询、筛选（日期/渠道/科目/账目）、分页 |
| V0-F6 | 最小汇总 | 渠道当月汇总、科目当月汇总（账户总览） |

### 2.4 V0 明确不做（边界）

- 不做登录/用户/家庭管理、不做账单、贷款汇总、完美账单、导入导出（归 V1/V2）。
- 不做 WebView 客户端（归后续）。
- 单用户：所有数据归属内置"默认用户（id=1）"，无鉴权。

## 3. 前端界面与交互说明（含界面草图）

### 3.0 导航设计（动态菜单，常用/不常用分组）

按**使用频率**将功能分为两组，采用"**顶部主导航 + 右上角动态下拉**"布局，**移除左侧长导航**，提升常用菜单识别度、避免布局浪费：

| 分组 | 菜单项 | 承载方式 |
| --- | --- | --- |
| **常用（核心记账）** | 账户总览、添加明细、明细列表 | **顶部一级 Tab 常驻展示** |
| **不常用（家庭级配置）** | 账目设置、渠道设置、科目设置 | **右上角「用户」下拉菜单**（V0 显示默认用户；V2 扩展家庭管理/密码/退出） |

设计要点：
- 常用三页顶部 Tab 直达，高亮当前项。
- 账目/渠道/科目属**家庭级配置**（`family_id` 绑定，V0 默认家庭），收进右上角「用户」下拉；V0 显示"默认用户"占位，V2 后该区域变为头像/用户名，下拉扩展家庭管理（成员/用户组/配置授权）、密码修改/退出登录，**布局不返工**。
- 用户下拉默认收起，点击展开为纵向菜单，点外部/再次点击收起。
- 内容区无左侧栏，记账操作占满宽度，常用项识别度更高。

### 3.3 页面交互说明

- **主导航 Tab**：点击切换「账户总览 / 添加明细 / 明细列表」，当前 Tab 高亮。
- **右上角「用户」下拉**：V0 显示"默认用户"（免登录占位）；点击展开纵向菜单（账目设置/渠道设置/科目设置——家庭级配置，V0 默认家庭），点击菜单项跳转对应设置页；点击页面空白或再次点击收起；V2 扩展家庭管理（成员/用户组/配置授权）/密码修改/退出登录。
- **账户总览**：选年/月或起止日期 → 点「汇总」刷新两块汇总；科目汇总按年月份行展示。
- **添加明细**：三 Tab 切换录入模式；单次行内填写；双次自动校验 from/to 金额绝对值相等（不等则红框提示）；分期填写期数/利率后提交；「向下复制」把上一行复制到下一行；「提交所选」批量提交勾选行。
- **明细列表**：筛选条件变更 → 查询；金额为负显示红/减号、为正显示黑/加号；修改进入编辑态，删除需确认。
- **设置页**：行内编辑保存，或新增行提交；删除被流水引用项时前端预提示"已被使用，不可删除"；可从「用户」下拉返回任意常用页。

## 4. 后端接口清单（V0）

> axum REST；V0 免登录，全部请求归属默认用户 id=1；账目/渠道/科目为家庭级配置（V0 归属默认家庭 family_id=1）。**金额一律以「分」（整数）传输**；前端输入元 → 提交转分，展示层分 → 元（两位小数）。

### 4.1 接口清单

**基础信息（trade / card / subject 三组结构一致）**

| 方法 | 路由 | 功能 | 关键入参 | 出参 | 错误码 |
| --- | --- | --- | --- | --- | --- |
| GET | `/api/trades` `/api/cards` `/api/subjects` | 列表 | `?active=1` | 数组（含 id、名称、激活等） | 200 |
| POST | 同上 | 新增 | 各资源字段 | 新建对象 | 201；400 参数错误 |
| PUT | `/{id}` | 修改 | 各资源字段 | 更新对象 | 200；400；404 |
| DELETE | `/{id}` | 删除 | — | 204 | 200；**409 被流水引用**；404 |

**记账**

| 方法 | 路由 | 功能 | 关键入参 | 出参 | 错误码 |
| --- | --- | --- | --- | --- | --- |
| POST | `/api/details` | 单次记账 | `trade_date, detail_desc, amount(分±), trade_id, subject_id, card_id, remark` | 新建流水 | 201；400 金额/引用错误 |
| POST | `/api/details/dual` | 双次记账 | `trade_date, detail_desc, from_amount, from_card_id, to_amount, to_card_id, trade_id, subject_id, remark` | 两条流水（同 trade_number） | 201；**400 from≠to** |
| POST | `/api/details/installment` | 分期记账 | `detail_desc, card_id, start_date, end_date, amount, months, interest_rate_year, repayment_method, remark` | 分期 + 逐期流水 | 201；400 |
| GET | `/api/details` | 明细列表 | `start_date, end_date, card_id, subject_id, trade_id, page, page_size` | `{list, total, page, page_size}` | 200 |
| PUT | `/api/details/{id}` | 修改流水 | 各字段 | 更新对象 | 200；400；404 |
| DELETE | `/api/details/{id}` | 删除流水 | — | 204（联动删除同 trade_number 关联流水） | 200；404 |

**分期查询**

| 方法 | 路由 | 功能 | 出参 | 错误码 |
| --- | --- | --- | --- | --- |
| GET | `/api/installments` | 分期记录列表 | 数组（含编号/渠道/金额/期数/利率/起止） | 200 |

**汇总**

| 方法 | 路由 | 功能 | 出参 | 错误码 |
| --- | --- | --- | --- | --- |
| GET | `/api/summary/channel` | 渠道汇总 | 每渠道：初余额、实时余额、已出账单、本月/下月未还、未出账单、额度、消费 | 200 |
| GET | `/api/summary/subject` | 科目汇总 | 按年月：科目 + 当月消费 | 200 |
| GET | `/api/summary/overview` | 账户总览 | `{channel_summary, subject_summary}` | 200 |

**系统**

| 方法 | 路由 | 功能 | 出参 |
| --- | --- | --- | --- |
| GET | `/api/health` | 存活探针 | `{status:"ok"}` |

## 5. 数据库设计（V0）

### 5.1 建表范围

V0 建 **7 张表**：`family, user, trade, card, subject, detail, installment`。`bill`、`merchant_type` 延后到 V1 以增量迁移补充。

### 5.2 表定义（SQLite）

> 金额一律 **INTEGER 存"分"（i64）**；日期/时间统一 TEXT ISO-8601；每表含 `id INTEGER PRIMARY KEY AUTOINCREMENT`；连接级 `PRAGMA foreign_keys=ON`。

**family**
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER PK | 家庭 id |
| family_name | TEXT | 家庭昵称 |
| created_at | TEXT | 创建时间 |

## 6. 核心业务逻辑（V0）

### 6.1 三类记账处理

| 类型 | 流水条数 | 逻辑 |
| --- | --- | --- |
| 单次（消费/收入/调账） | 1 | 写一条 detail |
| 双次（还款/调账） | 2 | from 渠道(负) + to 渠道(正) 两条 detail，同一 `trade_number` |
| 分期 | ≥2 | 生成一笔 installment + 按期生成多条 detail（同 `trade_number`） |

> 双次与分期在**同一 SQLite 事务**（`BEGIN IMMEDIATE`…`COMMIT`）内完成，任一步失败整体回滚。

### 6.2 金额约定与校验

- 支出（from/消费）为**负**；收入（to/收入）为**正**；以**分（整数）**存储与计算。
- 双次交易强校验 from 与 to 金额**绝对值相等**（还款/调账），否则 400。
- 分期金额、期数、利率为正数；`trade_date` 合法日期；金额禁止为 0（除非允许零值则显示提醒）。

### 6.3 汇总逻辑

- 渠道汇总：`初始余额 + Σ收入 - Σ支出` → 实时余额；按账单日/还款日划分已出/本月未还/下月未还/未出账单。
- 科目汇总：`GROUP BY subject_id + strftime('%Y-%m', trade_date)` 得各科目当月消费合计。
- 账户总览：组装渠道汇总 + 科目汇总两块。

### 6.4 删除保护

- 渠道/科目/账目被流水引用时禁止硬删，返回 409；提供停用（is_active=0）替代。
- 删除双次/分期流水时，联动删除同 `trade_number` 的关联流水（同一事务）。

## 13. V2 展望：家庭 / 用户组 / 配置授权模型

> 需求决策已于 2026-10-25 确认，并沉淀至《原始需求》3.8。本节给出其在开发侧的完整落地设计（表结构草案 + 迁移策略），V2 详设时以此为基础细化。

### 13.1 模型结构

```
家庭 Family
 ├─ 用户组 FamilyGroup     （如：全家 / 长辈 / 孩子 / 管理员组）
 ├─ 成员 User              （归属家庭；可归属多个组；isFamilyHead=家庭管理员）
 ├─ 家庭级配置 Trade/Card/Subject（family_id 绑定，管理员维护）
 └─ 配置↔组关联 TradeGroup/CardGroup/SubjectGroup（多对多）
```

### 13.2 已确认决策

1. 配置（账目/渠道/科目）为**家庭级**，归属 `family_id`，由家庭管理员维护。
2. **成员 ↔ 组：多对多**——一个成员可属于多个用户组。
3. **配置 ↔ 组：多对多**——一个配置可关联多个用户组（如"餐饮"科目全家可见、"孩子零花钱"仅孩子组）。
4. 管理员**天然全可见 + 全可管**；管理员默认属于"管理员组"，管理员组可有多个管理员。
5. 普通成员：家庭级配置**只读可用**，记账时下拉仅出现其所属组关联的配置。
6. **平台超管为预留能力，本期（V0/V1/V2 家庭功能）不实现**：家庭管理员为系统内最高权限；仅当系统成为公网多家庭服务时启用（见 13.7）。
7. **单家庭约束**：一个用户有且仅属于一个家庭（`family_id` 单值）。
8. **新家庭种子**：建立家庭时自动创建「管理员组+全员组」，预置账目（消费/收入/调账）、科目（餐饮/交通/日用品等），渠道留空。
9. **流水为用户级**：流水由人产生，与 `user_id` 绑定，无"家庭级流水"；个人流水仅本人可见与维护。
10. **用户组不支持嵌套**：家庭内用户组为扁平结构。
11. **配置停用即全组不可见**：配置停用后对其关联的所有用户组均不可见、不可用。
12. **加入方式为申请审批**：访客提交加入家庭申请，家庭管理员审批通过后加入并分配用户组。

### 13.3 用户角色定位

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| 系统状态 | 访客 / 正式成员 | `have_family`：访客未绑定家庭，不可记账；正式成员已归属家庭 |
| 家庭内角色 | 家庭管理员 / 普通成员 | `is_family_head`：管理员天然全可见、全可管，默认属「管理员组」 |
| 用户组身份 | 一个或多个用户组 | 决定正式成员的配置可见/可用范围（所属组配置并集） |
| 平台角色（预留） | 普通 / 平台超管 | `system_role`，本期不实现 |

角色组合规则：
- 访客不可能是家庭管理员（管理员身份必须归属家庭）。
- 正式成员加入时由管理员分配用户组（默认「全员组」）。
- 家庭管理员即使未加入某用户组，也天然可见全部配置。

用户旅程：注册 → 访客（可建立家庭成为管理员，或提交申请经审批加入）→ 正式成员获得家庭内功能权限；访客不可记账（详见原始需求 3.8）。

### 13.4 权限规则

| 操作 | 家庭管理员 | 普通成员 |
| --- | --- | --- |
| 配置（账目/渠道/科目）增删改 | 全量 | 否 |
| 配置可见 / 记账可用 | 全部配置 | 仅其所属组关联的配置 |
| 用户组 / 成员管理 | 是 | 否 |
| 个人流水 | 本人记账/查看 | 本人记账/查看 |

可见性公式：`成员可见配置 = 该成员所属全部组关联配置的并集`。

### 13.5 表结构草案（V2 增量迁移）

| 表 | 说明 |
| --- | --- |
| `family_group` | 用户组：id、family_id FK→family、group_name、group_desc、created_at |
| `user_group` | 成员↔组（多对多）：user_id、group_id、created_at |
| `trade_group` / `card_group` / `subject_group` | 配置↔组（多对多）：cfg_id、group_id |
| Trade / Card / Subject | V0 起即 `family_id` 归属；`user_id` 为创建人（审计） |
| User | `is_family_head`、`family_id` 沿用（V0 已具备） |

### 13.6 迁移与兼容

- V2 迁移 `003_*.sql`：建 `family_group` / `user_group` / 配置↔组关联表；创建默认「管理员组」并把默认用户加入；创建默认「全员组」并把既有全部配置关联到全员组——**老数据即刻可见，字段语义零迁移**。
- V0 数据文件直接升级，无需数据重导。

### 13.7 平台超管（预留边界）

> 边界声明：家庭管理员为系统内最高权限；**平台超管本期（V0/V1/V2 家庭功能）不实现**，仅当系统演变为"一个平台、多家庭注册入驻"的公网服务时启用。

- 角色字段：`user.system_role`（NULL=普通成员 / `super_admin`=平台超管），**独立于** `is_family_head`（家庭管理员），两者互不干扰。
- 超管能力（届时定义）：全量家庭/用户查询、重置成员、停用家庭、数据导出、操作审计日志。
- 入口：独立 `/admin` 后台（与记账主站隔离），而非用户下拉。
- 表：`user.system_role` 字段 + `audit_log`（操作审计日志表），无需新增复杂结构。
